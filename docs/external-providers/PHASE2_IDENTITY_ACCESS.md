# Phase 2 — Persistent external identity and governed access
Branch: `codex/external-provider-platform-20261009`; consolidated draft PR #560 to `main`. No phase PR merges.

## Architectural contracts
- Global `external_identities` is unique by normalized email. It is separate from `users`; external authentication never mints a staff JWT, certifying-staff authorization, QMS approval or employee role.
- Global `external_credentials` uses the existing Argon2id hash/policy. TOTP seeds use Fernet encryption derived from configured application SECRET_KEY. Identity may belong to multiple `external_organizations` through explicit `external_organization_memberships`.
- An AMO provider is **still** the authoritative `procurement_suppliers` row. Global organizations link to one or more tenant suppliers through `external_tenant_providers`; no fuzzy auto-merge by name. Tenant grants live in `external_tenant_grants` and carry role, tightly bounded capabilities, exact object-scope lists, status, Quality approver and optimistic version.
- Vendor key = the tenant's `procurement_suppliers.supplier_code`, not a secret; it is always combined with tenant, email and password. If one email has multiple provider grants in a tenant, a vendor key is mandatory to select one.
- Email ownership comes from one-use expiring codes delivered via the existing essential email service, **not** query-string secrets. Quality grant approval and provider portal activation are distinct from Procurement commercial activation and existing supplier Quality approval. Provider administrators can invite members only within their own active tenant organization, never auto-approve accounts or mint internal privileges.
- `external_sessions` stores SHA-256 hashes of random tenant-hinted cookie tokens and CSRF secrets, expiration, revocation, last-used and MFA verification. Cookie is HttpOnly, Secure in production and Strict same-site with the external API path. Every request checks tenant/provider/identity/membership/grant state and restrictions under PostgreSQL FORCE RLS. State changes immediately invalidate sessions. Session rotation rejects previous tokens.
- Explicitly suspended portal access permits only session/profile continuity and the narrowly delegated `capa.respond` capability. No new contract, procurement or QMS approval operations are authorized by this exception.
- Global credential changes revoke the identity's sessions **across AMOs**, respecting RLS by switching transaction-local tenant context, and invalidate outstanding reset codes across AMOs. Tenant Quality cannot globally lock or unlock another AMO's identity; shared-identity credential recovery uses verified email and separately approved tenant grants.
- TOTP enrollment requires the current password and a correct 6-digit confirmation. Login enforces TOTP when enabled. Provider member management requires recent verified MFA. The existing `webauthn` verifier is reused for passkey registration and step-up assertions with RP/origin validation, one-use five-minute challenges, user-verification requirement, credential public key and monotonic sign counter. Passkeys are step-up factors; password login is retained.
- `external_security_events` records attributable, tenant RLS-guarded events, with a PostgreSQL UPDATE/DELETE prevention trigger; token/code/secret/password values are excluded. The existing audit invitation passkey flow is **not** silently converted into vendor authorization.

## Working surfaces added
- Vendor: `/vendor/login`, `/vendor/invite`, `/vendor/forgot`, `/vendor/reset`, `/vendor/verify` and `/vendor/account`.
- Vendor account: profile display name, password change, TOTP, WebAuthn passkey registration/step-up, session list, one-session/all-session revocation, delegated member directory and member invitations/revocations. Actions use real APIs and session-bound CSRF.
- Internal Quality: `/maintenance/:amoCode/quality/external-accounts` for per-tenant representative invitations, approval/restore/suspension/revocation, provider portal activation/suspension, restrict-new-work controls, re-verification, privilege editing, login unlock and security event history.
- Phase 1 supplier profile provides a navigation link to the Quality screen; Phase 1 edits were also corrected to retain boolean `is_primary` and JSON requested scopes.
- New routes are included in `backend/amodb/main.py`; the vendor public route uses no `RequireAuth` staff JWT, while the Quality route uses the existing staff role/session framework.

## Actual limitations / operational configuration
1. **No tests, builds, lint, manual CI or Alembic operations were run.** This is a static source implementation; all runtime and configuration claims remain unverified until Phase 10. GitHub may automatically start Actions on commits.
2. A production deployment MUST supply `SECRET_KEY`, shared distributed auth rate limiting (`AUTH_RATE_LIMIT_REDIS_URL` and enforce shared policy), configured existing ESSENTIAL email delivery, HTTPS and same-origin vendor API access. Email API responses distinguish `SENT` from `SKIPPED_NO_PROVIDER`/delivery failure; an issued invitation is not proof an email was received.
3. External WebAuthn requires `EXTERNAL_WEBAUTHN_RP_ID` and `EXTERNAL_WEBAUTHN_ORIGINS` in production. Full passwordless/passkey-first login is **not** claimed; passkey registration and step-up second-factor verification are implemented by source, with runtime acceptance deferred.
4. No generic provider access to procurement, supplier contracts, DMS documents or QMS workflows is granted merely by authentication. Provider business endpoints in later phases must explicitly call `require_provider(capability)` **and** `scope_allows(contract_id=…,document_id=…,assignment_id=…)`, then enforce record ownership, approval state and controlled document revocation in SQL/backend. Hiding UI is never a substitute.
5. Exact Safarilink vendor register and contracts workbooks remain absent; Phase 1 source-specific reconciliation is still unverified.
6. Existing prior five cross-module CI browser failures on PR #560 were separately investigated; no new manual test claim is made here. Phase 2 changes affect the same branch and may auto-trigger CI, which will be reviewed only under the permitted verification workflow.

## Source reconciliation and final static hardening
- Upstream `main` was integrated into the same feature branch on 12 October 2026. The QMS audit checklist N/C handling and browser-based offline preparation/checklist import now coexist with this branch's previous evidence-acceptance safeguards.
- Delegation enforces a per-key subset of the acting Provider Administrator's exact tenant-scoped `contracts`, `documents` and `assignments`, in addition to the allowed capability intersection. A Provider Administrator cannot invent object IDs for subordinate grants.
- The vendor session checks the canonical Procurement supplier lifecycle and the imported-supplier activation hold; it restricts new delegated operations unless that supplier is active and approved or conditionally approved. A prospective or suspended supplier's portal account is not sufficient for operational authority.
- Quality Manager and Quality Officer tenant read/invitation access now matches the QMS frontend route guard; only the Quality Manager may approve, restore, suspend, revoke or edit account/provider privileges.
- TOTP/passkey-enrolled identities require a recent second factor when changing a password or adding another factor. Invitation acceptance, verified-email code redemption, password changes and MFA enrollment are rate limited.
- Essential email delivery re-establishes transaction-local tenant context after the invitation/verification commit. Revoked session cookies can be discarded through logout without reactivating access.
- `/vendor/denied` and `/vendor/revoked` are dedicated navigable views backed by current session authorization responses, rather than implying that a stale client-side token confers access.
