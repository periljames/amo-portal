# Tenant QMS Settings

Settings now has persistent Overview, Workflows & approvals, Numbering, Notifications and Retention tabs, with icons, tenant identity, access status and short control descriptions. Generic JSON-derived controls have been replaced by controls connected to the workflows that consume them.

Numbering configures audit, Quality CAR, reliability CAR and finding prefixes, plus sequence width and date presentation (`YY`, `YYYY`, `YYYY-MM`, `YYYYMM`, `YYMM`). Audit/CAR series are scoped by tenant, prefix, unit/scope and the server calendar year. The internal annual counter remains compatible with existing records. Findings count within their parent audit and finding marker. New values apply to new references; existing references are never rewritten. The older Audit Scopes editor and Settings synchronize audit prefixes in the same transaction.

Series controls accept a last-issued number of zero for a fresh series (next number 1). They require a reason, explicit confirmation and an unchanged last-issued snapshot. The server rejects lowering the counter below an issued reference, including soft-deleted records. Users can select a new prefix for a fresh series. Database primary-key/index sequences are never reset. PostgreSQL transaction advisory locks serialize allocation and counter/configuration changes; finding allocation uses an audit-specific lock. Missing/low counters reconcile against issued audit/CAR references before allocating.

Follow-up controls edit actual report deadlines, separate report reminder values, CAR percentage milestones and the final reminder interval. Escalation remains governed. Notifications embeds the existing sender/reply-address configuration, including individual add/remove email controls. Sending a test email is an explicit separate action; none is sent for this review. Retention controls preserve the existing MOPM floors and allow tenant extensions only.

The new Settings forms compare expected saved values on the server, retain drafts after errors and expose errors inline without duplicate global notifications. Saves update local state and invalidate related workflow/scope caches. Counter refreshes bypass stale caching. Tenant view/manage permissions remain enforced by the API, including for direct requests.

Verification evidence is kept outside Git under `.artifacts`. Backend checks cover reference allocation, tenant isolation, prefix compatibility, stale updates, invalid values, preservation of issued references and fresh-series initialization. Browser checks distinguish isolated role fixtures from the real authenticated tenant. Production counters are not reset to demonstrate the feature.


Reference dates are generated from the server UTC clock at issuance, independently of client clocks and planned audit dates. The year/month are never editable values. Settings shows the server date and selectable format examples; `YYYY-MM` provides an ISO year/month form. Changing presentation, or moving to another month, keeps the annual sequence. A new server calendar year starts its own counter automatically. Reset requests assert the expected server period and format and reject manually supplied date fields. Historical series are view-only. Audit scopes are selected from active tenant scopes; CAR units are derived from the tenant. Save a new prefix in formats before initialising that series. Audit Scopes previews also use server-generated date/width metadata. Rescheduling an audit alone no longer regenerates its reference.

Live verification on October 26 used the supplied staff administrator at the public portal. The production build was deployed and visually reviewed at desktop and 390-pixel mobile widths. The server date displayed `2026-10-26`. Saving `YYYY-MM`, reloading, and reading the audit-scope preview produced `QAR/MO/2026-10/007`. The format was then restored to `YY`. All six counter snapshots remained unchanged, and both audit references present before this review remained present afterward. A zero reset against an issued series returned the expected 409 with one inline error. No production counter was reset. CAR unit `SAF` was derived, and audit scopes came from the tenant's active list. Readiness returned 200 with database and broker connected.

The exact deployed source passed the production TypeScript/Vite build. Backend verification passed 53 checks, followed by one additional passing legacy-counter reconciliation check. Browser verification passed 22 of 23 scenarios; the remaining failure was an ambiguous test-only status locator after adding an HTML output element. Its corrected Settings suite passed all five scenarios. The 43 shared-register route checks, readonly/normal-user cases and vendor entry checks use isolated fixtures; they do not certify every live business workflow. No email was sent. Reports and broader workflow review remain separate work.
